## BiblePlaylist Project Architecture Blueprint\n\n### Purpose\nThe document serves as an in-project technical specification and architectural overview for the `BiblePlaylist` Blazor WASM client. It captures the complex state management patterns, service dependencies, and critical timings required to maintain or extend this application.\n\n### Core Components & Responsibilities (Review Scope)\n*   **State Management:** Global state is derived from a combination of local storage (`blazored-localstorage`) for persistence and internal event buses (`IDelegateLibrary`). State changes are asynchronous events, requiring careful ordering to prevent race conditions.\n*   **UI Shell:** `MainLayout.razor` initializes services and defines the overall structure.\n*   **Playback Core (Critical):** `AudioPlayer.razor` manages the entire media lifecycle (Chapter $\Rightarrow$ Segment $\Rightarrow$ Verse). It orchestrates audio playback, TTS narration timing, and navigation logic using internal timers and JS Interop calls to manage smooth transitions.\n\n### Critical Workflow: Audio Synchronization & Synchronization Points\n1.  **Goal:** Play segmented audio/narration based on user selection (Playlist/Chapter).\n2.  **Process:** User action triggers `PlayCurrentSegment()` $\rightarrow$ State Update $\rightarrow$ **TTS Narration** (`speakSequenceAsync`) runs -> Wait until TTS finishes -> Load actual background audio track (`audioPlayer.ReloadAsync`) -> Start the observation timer (`Timer`).\n3.  **Observability Hook:** The component must continuously read `window.AudioCurrentTime` from JS Interop via a ticking timer (`UpdatePlaybackPosition`), triggering UI updates (scrolling to verse) and checking for segment boundaries.\n4.  **Cleanup/Guard:** When navigation occurs or playtime is manually paused, an explicit cleanup routine *must* be executed to **cancel all active speech synthesis calls and stop the audio element** before proceeding with new data loading. This prevents race conditions.\n\n### Key Protocols & Pitfalls (Must Memorize)\n1.  **Timing:** The system relies on a $300 \text{ms}$ polling timer synchronized with `window.AudioCurrentTime` to detect precise segment/verse boundaries.
2.  **Persistence:** All state synchronization must obey: Local read $\rightarrow$ Memory/Storage write (e.g., saving version data (`Version/SaveVerses`)).\n3.  **Cleanup:** The failure to gracefully shut down audio and speech synthesis is the primary instability risk.\n\n---"
